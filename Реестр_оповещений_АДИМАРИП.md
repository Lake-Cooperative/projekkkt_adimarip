**Реестр оповещений «АДИМАРИП»**

Use Cases, функции системы и их описание

# 1. Общие сведения

Система представляет собой клиент-серверное веб-приложение для учета электронных оповещений, их статусов, истории изменений, обращений и сопроводительных документов.

Проект является учебным и демонстрационным, и работает с тестовыми данными.

Технологический стек: React 18 + TypeScript + Vite (frontend); ASP.NET Core 8 Web API (backend); Entity Framework Core 8; PostgreSQL 16; JWT-аутентификация; Swagger/OpenAPI; Docker Compose.

# 2. Должности и роли

| **Должность**                  | **Роль в системе**  | **Права**                                                             |
|---|---|---|
| Секретарь                      | Operator            | Чтение и изменение данных                                             |
| Управитель                     | Manager             | Чтение и изменение данных; просмотр истории и контроля                |
| Служащий                       | Observer            | Чтение и возможность подачи документов                                |
| DevOps / инженер автоматизации | Automation Engineer | Создание учетных записей; запуск проекта и проверка работоспособности |

# 3. Варианты использования

## UC-00. Вход в систему

**Должность:** Все пользователи системы.

**Предусловие:** пользователь ещё не прошёл аутентификацию.

**Основной поток:** пользователь выбирает вход через указание логина и пароля; система получает результат аутентификации, создаёт JWT и предоставляет доступ в соответствии с назначенной ролью.

**Результат:** пользователь вошёл в систему; JWT используется для последующих запросов.

## UC-01. Создание адресата

**Должность:** Секретарь.

**Предусловие:** адресат с таким идентификатором отсутствует.

**Основной поток:** Секретарь вводит ФИО, дату рождения, контакты и адрес; система проверяет уникальность идентификатора и сохраняет данные.

**Результат:** созданы записи Recipient и Address.

**API:** POST /api/recipients.

## UC-02. Создание оповещения

**Должность:** Секретарь.

**Предусловие:** существуют адресат и подразделение.

**Основной поток:** Секретарь задаёт номер, даты, причину и комментарий; система валидирует данные и сохраняет оповещение; создаёт начальную запись истории статусов; записывает audit event.

**API:** POST /api/notices.

## UC-03. Просмотр реестра

**Должность:** Секретарь, Управитель, Служащий.

**Результат:** таблица оповещений с фильтрацией по статусу, подразделению и строке поиска, с серверной пагинацией.

**API:** GET /api/notices.

## UC-04. Просмотр карточки оповещения

**Результат:** отображаются адресат, подразделение, дата создания, срок, текущий статус, история статусов, уведомления и обращения.

**API:** GET /api/notices/{id}.

## UC-05. Изменение статуса

**Должность:** Секретарь.

**Правило:** каждый переход фиксируется в NoticeStatusHistory и AuditEvent.

**API:** PATCH /api/notices/{id}/status.

## UC-06. Отправка mock-уведомления

**Основной поток:** Секретарь выбирает канал; система создаёт Notification и DeliveryAttempt со статусом Delivered. Реальная отправка SMS/e-mail не выполняется.

**API:** POST /api/notices/{id}/notifications.

## UC-07. Регистрация обращения

**Основной поток:** Секретарь фиксирует тип обращения и текст; обращение привязывается к оповещению и получает статус Submitted.

**API:** POST /api/notices/{id}/appeals.

## UC-08. Добавление документа

**Основной поток:** сохраняются метаданные документа: имя, MIME type, URI/идентификатор хранилища. Бинарный файл в MVP не принимается.

**API:** в API-контракте отдельный endpoint не описан (см. раздел 5).

## UC-09. Просмотр истории

**Должность:** Управитель.

**Результат:** последовательность изменений статусов и аудит действий.

**API:** данные приходят в составе GET /api/notices/{id}.

## UC-10. Проверка работоспособности

**Должность:** DevOps / инженер автоматизации.

**Основной поток:** выполняется docker compose up --build; открываются UI (порт 8080), API (порт 8081) и Swagger (/swagger).

**API:** GET /api/health.

## UC-11. Создание учетной записи

**Должность:** Инженер автоматизации.

**Предусловие:** создаваемый пользователь ещё не имеет учетной записи.

**Основной поток:** инженер автоматизации создаёт учетную запись пользователя и назначает ей одну из предусмотренных ролей; самостоятельная регистрация пользователей в системе отсутствует.

**Результат:** создана учетная запись.

**API:** служебная функция управления учетными записями.

# 4. Функции системы

| Авторизация | **Ролевой контроль доступа** <br> Role-based access | Все endpoint, кроме входа и проверки работоспособности, требуют JWT Bearer. Доступ и операции определяются ролью пользователя; создание учетных записей доступно только инженеру автоматизации. | UC-00, UC-01–UC-09, UC-11 | Operator, Manager, Observer, Automation Engineer |

| Адресаты | **Создание адресата** <br> POST /api/recipients | Создаёт адресата с уникальным идентификатором, ФИО, датой рождения, контактами (e-mail, телефон) и вложенным адресом (индекс, регион, город, улица, дом, квартира). Система проверяет уникальность идентификатора; создаются записи Recipient и Address. | UC-01 | Operator, Manager |
| Подразделения | **Получение списка подразделений** <br> GET /api/offices | Возвращает список подразделений. Используется для выбора подразделения при создании оповещения и для фильтрации реестра. | UC-02, UC-03 | Operator, Manager, Observer |
| Оповещения | **Просмотр реестра оповещений** <br> GET /api/notices | Таблица оповещений с фильтрами по статусу (status), подразделению (officeId) и строке поиска (search), с серверной пагинацией (pageSize 1–100). Ответ: items, page, pageSize, total, totalPages. | UC-03 | Operator, Manager, Observer |
| Оповещения | **Просмотр карточки оповещения** <br> GET /api/notices/{id} | Детальная карточка: адресат, подразделение, дата создания, срок обработки, текущий статус, история статусов, уведомления, обращения, документы и аудит. Если оповещение не найдено — 404. | UC-04 | Operator, Manager, Observer |
| Оповещения | **Создание оповещения** <br> POST /api/notices | Принимает номер, адресата, подразделение, автора, дату создания, срок обработки и комментарий. Ошибки: 400 (срок раньше даты создания, пустая причина), 404 (адресат или подразделение не найдены), 409 (номер уже существует). | UC-02 | Operator, Manager |

| Обращения | **Регистрация обращения** <br> POST /api/notices/{id}/appeals | Фиксирует тип обращения/обжалования (например, Clarification) и текст; обращение привязывается к оповещению и получает статус Submitted. Пустой текст — 400. | UC-07 | Operator, Manager |

| История и аудит | **Просмотр истории и аудита** <br> GET /api/notices/{id} | Последовательность изменений статусов и аудит действий пользователей. Отдельного endpoint нет: данные приходят в составе карточки оповещения. | UC-09 | Manager (Управитель) |
| История и аудит | **Ведение журнала аудита** <br> AuditEvent (внутренняя функция) | Автоматическая запись ключевых действий пользователей (в том числе создания оповещения и смены статуса). Вызывается системой и не имеет собственного endpoint'а. | UC-02, UC-05 | Система |
| Служебные | **Проверка работоспособности** <br> GET /api/health | Проверка корректной работы сервиса без авторизации; ответ: status ok и имя сервиса. Используется после запуска docker compose up --build (UI — порт 8080, API — порт 8081, Swagger — /swagger). | UC-10 | DevOps / инженер автоматизации |

Коды ошибок API:

- 400 Bad Request — некорректные данные: срок раньше даты создания, пустая причина или текст обращения, неизвестный канал уведомления, некорректный JSON;

- 401 Unauthorized — отсутствует или истёк JWT;

- 403 Forbidden — роль не даёт права на изменение (Служащий);

- 404 Not Found — не найдено оповещение, адресат или подразделение;

- 409 Conflict — конфликт бизнес-правил: дубликат номера, повторная установка текущего статуса.
