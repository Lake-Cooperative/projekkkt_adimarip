# Системные требования
## Проект «Реестр оповещений „АДИМАРИП“»

**Статус:** черновик v0.1
**Источники:** [`business-requirements.md`](business-requirements.md) (далее — БТ), [`UseCasesANDFunctions.md`](UseCasesANDFunctions.md) (далее — UC).
**Назначение:** определить, *как* система должна реализовать бизнес-требования: функции, API, данные, ограничения и нефункциональные требования.

> **Как читать пометки.** Требования без пометки прямо следуют из БТ или UC (в скобках указан источник). Пометка **[ПРЕДЛОЖЕНО]** означает, что в источниках этого нет и решение нужно подтвердить. Пометка **[ВОПРОС]** означает, что источники противоречат друг другу или молчат (см. раздел 10).

---

## 1. Область применения

Клиент-серверное веб-приложение для учёта электронных оповещений, их статусов, истории изменений, уведомлений, обращений и метаданных сопроводительных документов (БТ §1, UC §1).

Система **учебная и демонстрационная**, работает с тестовыми данными (БТ §5 п.14). Не входит в объём:

- реальная отправка SMS и e-mail (БТ §4.7, БП-12);
- загрузка и хранение бинарного содержимого документов (БТ §4.9, БП-13);
- самостоятельная регистрация пользователей (БТ §3.4, БП-11);
- промышленная эксплуатация (БТ §5 п.14).

## 5. Функциональные требования

### 5.1. Аутентификация и авторизация

| ID | Требование | Источник |
|---|---|---|
| SR-AUTH-01 | Пользователь входит по логину и паролю. | UC UC-00, БТ §4.1 |
| SR-AUTH-02 | При успешном входе система выдаёт JWT и возвращает отображаемое имя, роль и время истечения токена. | UC §4 |
| SR-AUTH-03 | Все endpoint, кроме входа и `GET /api/health`, требуют действительный JWT. Без токена или с истёкшим токеном — **401**. | UC §4, §6 |
| SR-AUTH-04 | Роль пользователя определяет допустимые операции (раздел 4). При нехватке прав — **403**. | БТ БП-10, UC §6 |
| SR-AUTH-05 | Самостоятельной регистрации нет. | БТ БП-11 |
| SR-AUTH-06 | Пароли хранятся только в виде хеша (например, PBKDF2 или bcrypt), в открытом виде не хранятся и не логируются. | **[ПРЕДЛОЖЕНО]** |
| SR-AUTH-07 | Секрет подписи JWT и строка подключения к БД задаются переменными окружения, а не хранятся в репозитории. | **[ПРЕДЛОЖЕНО]** |

### 5.3. Адресаты

| ID | Требование | Источник |
|---|---|---|
| SR-REC-01 | `GET /api/recipients?search=` ищет адресатов по строке. Если ничего не найдено, возвращается **200** и пустой список. | UC §4 |
| SR-REC-02 | `POST /api/recipients` создаёт адресата: уникальный идентификатор, ФИО, дата рождения, контакты (e-mail, телефон), вложенный адрес (индекс, регион, город, улица, дом, квартира). | UC §4, БТ §4.2 |
| SR-REC-03 | Идентификатор адресата уникален. При дубликате создание отклоняется. Код ответа — **409** (по аналогии с номером оповещения). | БТ БП-1, **[ПРЕДЛОЖЕНО]** код |
| SR-REC-04 | Создание адресата порождает две записи: `Recipient` и `Address`. Операция атомарна: либо обе записи, либо ни одной. | UC UC-01, **[ПРЕДЛОЖЕНО]** атомарность |

## 6. Модель данных

Сущности названы в UC. Перечень атрибутов — минимум, следующий из БТ и UC; типы и ограничения уточняются при проектировании схемы.

| Сущность | Ключевые атрибуты | Связи |
|---|---|---|
| `User` | логин, хеш пароля, отображаемое имя, роль | — |
| `Recipient` | уникальный идентификатор, ФИО, дата рождения, e-mail, телефон | 1:1 `Address` |
| `Address` | индекс, регион, город, улица, дом, квартира | принадлежит `Recipient` |
| `Office` | идентификатор, название | 1:N `Notice` |
| `Notice` | уникальный номер, дата создания, срок обработки, причина, комментарий, текущий статус, автор | N:1 `Recipient`, N:1 `Office` |
| `NoticeStatusHistory` | статус, комментарий, время, автор | N:1 `Notice` |
| `AuditEvent` | действие, пользователь, время, объект | N:1 `Notice` (для событий оповещения) |
| `Notification` | канал, адрес получателя | N:1 `Notice`, 1:N `DeliveryAttempt` |
| `DeliveryAttempt` | статус (`Delivered`), время | N:1 `Notification` |
| `Appeal` | тип, текст, статус (`Submitted`) | N:1 `Notice` |
| `Document` | имя, MIME type, URI/идентификатор хранилища | N:1 `Notice` |

Ограничения целостности: уникальность идентификатора адресата и номера оповещения (SR-REC-03, SR-NTC-06); `Notice.дата_срока ≥ Notice.дата_создания` (БП-3); `Notice.причина` не пуста (БП-4).

## 7. Правила валидации и коды ответов

| Код | Когда возвращается | Источник |
|---|---|---|
| 200 | Успешное чтение, в том числе пустой результат поиска адресатов | UC §4 |
| 201 | Успешное создание ресурса | **[ПРЕДЛОЖЕНО]** |
| 400 | Некорректные данные: срок раньше даты создания, пустая причина или текст обращения, неизвестный канал, некорректный JSON | UC §6 |
| 401 | Нет JWT или он истёк | UC §6 |
| 403 | Роль не даёт права на операцию (например, Observer пытается изменить данные) | UC §6 |
| 404 | Не найдено оповещение, адресат или подразделение | UC §6 |
| 409 | Дубликат номера оповещения (или идентификатора адресата), повторная установка текущего статуса | UC §6 |

Формат тела ошибки единый для всех endpoint (например, `application/problem+json`). **[ПРЕДЛОЖЕНО]**

## 8. Нефункциональные требования

В источниках нефункциональных требований с числовыми значениями нет. Всё ниже — **[ПРЕДЛОЖЕНО]**, кроме указанного явно.

| ID | Категория | Требование |
|---|---|---|
| SR-NFR-01 | Безопасность | Все защищённые endpoint проверяют JWT и роль на стороне сервера; скрытие кнопок в UI не заменяет проверку на API (следует из БТ БП-10). |
| SR-NFR-02 | Безопасность | Входные данные валидируются на сервере; запросы к БД параметризованы (EF Core). |
| SR-NFR-03 | Безопасность | Срок жизни JWT ограничен и возвращается клиенту (UC §4); значение задаётся конфигурацией. |
| SR-NFR-04 | Производительность | Реестр всегда загружается постранично (БТ §4.4); на тестовом наборе до 10 000 оповещений отклик списка — не более 1 с. Значение ориентировочное и уточняется. |
| SR-NFR-05 | Надёжность | Операции с несколькими записями (создание оповещения, смена статуса, создание адресата) выполняются в одной транзакции. |
| SR-NFR-06 | Сопровождаемость | API описан в OpenAPI; изменения контракта отражаются в Swagger автоматически. |
| SR-NFR-07 | Развёртываемость | Запуск с нуля одной командой `docker compose up --build` без ручной настройки на чистой машине с Docker (UC UC-10). |
| SR-NFR-08 | Совместимость | UI работает в актуальных версиях Chrome, Firefox, Edge. |
| SR-NFR-09 | Локализация | Интерфейс на русском языке; даты отображаются в формате ДД.ММ.ГГГГ. |
| SR-NFR-10 | Данные | Персональные данные в БД — только вымышленные тестовые. |
| SR-NFR-11 | Тестируемость | Для бизнес-правил БП-1…БП-10 есть автоматические тесты API (положительный и отрицательный сценарий). |

## 10. Открытые вопросы и расхождения в источниках

Здесь собраны места, где БТ и UC противоречат друг другу или молчат. Пока их нет в таблице решений, реализация идёт по значению из колонки «Временное решение».

| № | Вопрос | Где видно | Временное решение |
|---|---|---|---|
| 1 | **Кто видит историю и аудит.** БТ §4.10 и UC-09 отдают их Управителю, но `GET /api/notices/{id}` доступен трём ролям и по UC §4 возвращает «аудит» всем. | БТ §4.10, UC UC-09, UC §4 | Поля `statusHistory` и `audit` возвращаются только Manager; для остальных ролей опускаются. |
| 2 | **Документы и Observer.** БТ §3.3 и таблица UC позволяют Observer «подавать документы», а UC §6 говорит, что Observer не может изменять данные (403). Endpoint добавления документа не описан. | БТ §3.3, §4.9, UC §6 | Observer может только `POST` документа; остальные изменяющие операции для него закрыты. |
| 3 | **Endpoint входа и учётных записей** не описаны в UC (в UC-00 нет строки «API», в UC-11 написано «служебная функция»). | UC UC-00, UC-11 | `POST /api/auth/login`; создание учётных записей — `POST /api/users` для Automation Engineer. |
| 4 | **Статусы оповещения** и допустимые переходы не определены. Известны только `Delivered` (доставка) и `Submitted` (обращение). | БТ §7 | Список статусов задаётся конфигурацией; любой переход, кроме повтора текущего, разрешён. |
| 5 | **Подразделения:** состав и правила ведения. | БТ §7 | Фиксированный список из начальных данных. |
| 6 | **Обязательные поля** адресата и оповещения. | БТ §7 | Обязательны поля, перечисленные в SR-REC-02 и SR-NTC-05, кроме комментария и квартиры. |
| 7 | **Типы обращений** и правила обработки. | БТ §7 | Свободная строка типа; пример — `Clarification`. |
| 8 | **Права Automation Engineer** на чтение реестра. | БТ §3.4, UC §4 («Роли» в строке авторизации перечисляют все четыре роли для UC-01…09) | Доступа к бизнес-данным нет. |
| 9 | **Автор оповещения** передаётся в запросе (UC §4) и одновременно известен из JWT. | UC §4 | Берётся из JWT (SR-NTC-09). |
| 10 | **Дублирование адресата:** код ответа в UC не указан. | БП-1 | **409**. |
| 11 | **Реальная отправка уведомлений** за пределами демо. | БТ §7 | Не реализуется. |
