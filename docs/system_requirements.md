## 1. Область применения

Клиент-серверное веб-приложение для учёта электронных оповещений, их статусов, истории изменений, уведомлений,
обращений, метаданных сопроводительных документов и массового оповещения работников (БТ §1, UC §1).

Система **учебная и демонстрационная**, работает с вымышленными данными (БТ §5 п.14). Не входит в объём:

- реальная отправка SMS и e-mail — доставка имитируется (БТ §4.7, БП-12);
- загрузка и хранение бинарного содержимого документов (БТ §4.9, БП-13);
- самостоятельная регистрация пользователей (БТ §3.4, БП-11);
- промышленная эксплуатация с реальными персональными данными (БТ §5 п.14).

### 5.7. Статусы и история

| ID | Требование | Источник |
|---|---|---|
| SR-STS-01 | `PATCH /api/notices/{id}/status` — новый статус и необязательный комментарий (до 4000). | UC §4, БТ §4.6 |
| SR-STS-02 | Каждый переход записывается в историю и аудит одной транзакцией (уровень Serializable). | UC-05, БП-7 |
| SR-STS-03 | Неизвестный статус — **400**; повтор текущего или запрещённый переход — **409**; не найдено — **404**; параллельное изменение той же записи — **409**. | UC §4, БП-6 |
| SR-STS-04 | Допустимые переходы задаёт конечный автомат: `Created→Sent/Cancelled`, `Sent→Delivered/Failed/Cancelled`, `Failed→Sent/Cancelled`, `Delivered→Read/Closed`, `Read→Closed`; `Closed`, `Cancelled` — конечные. | SR-STS-05 | Записи истории и аудита через API не изменяются и не удаляются. | [РЕШЕНИЕ] |
| SR-STS-06 | Работник подтверждает получение своего оповещения (`POST /api/notices/{id}/acknowledge`): статус доводится до `Read` через разрешённые переходы, фиксируется событие `Acknowledged`. Повтор — **409**, чужое — **404**. | [M12] |

### 5.9. Массовое оповещение работников [M12]

| ID | Требование |
|---|---|
| SR-BRD-01 | `POST /api/broadcasts` принимает заголовок (3–200), текст (до 4000), важность (`Info`/`Warning`/`Critical`), каналы, подразделение-отправитель и аудиторию (`All` / `Offices` / `Recipients`). |
| SR-BRD-02 | Аудитория — действующие (не списанные) адресаты; не более 2000 за рассылку (**400**). Предварительный подсчёт — `POST /api/broadcasts/preview`. |
| SR-BRD-03 | Для каждого работника создаётся оповещение реестра (номер `{код рассылки}-{ID адресата}`, срок 1 день для `Critical`, иначе 3) и уведомления по плану доставки — одной транзакцией. |
| SR-BRD-04 | План доставки: выбранные каналы, для которых у работника есть контакт (e-mail — `Email`; телефон — `Sms`, `Max`); если ни одного — канал `Portal`. Для `Critical` — все каналы с известным контактом. |
| SR-BRD-05 | Ответ — **202 Accepted** сразу после регистрации; доставка выполняется в фоне. |
| SR-BRD-06 | Фоновый обработчик: приоритетная очередь (`Critical` → `Warning` → `Info`, внутри — по порядку), 2 одновременно обрабатываемые рассылки, до 16 параллельных отправок, порции по 100 оповещений. |
| SR-BRD-07 | По итогам доставки оповещение переходит `Created → Sent → Delivered` (хотя бы один канал доставил) или `→ Failed`. Подтверждение работника, пришедшее раньше, не перезаписывается. |
| SR-BRD-08 | После перезапуска API незавершённые рассылки продолжаются; уже доставленные уведомления повторно не отправляются. |
| SR-BRD-09 | `GET /api/broadcasts/{id}` — сводка, прогресс (доставлено, ошибки, в очереди, подтвердили) с разбивкой по каналам и до 100 недоставленных уведомлений с причиной. |
| SR-BRD-10 | Работнику срочные неподтверждённые оповещения показываются баннером с кнопкой «Ознакомлен(а)». |

## 6. Модель данных

Полная схема — [`erd.md`](erd.md). Ключевые сущности:

| Сущность | Ключевые атрибуты | Связи |
|---|---|---|
| `AppUser` | логин (PK), хеш пароля, имя, роль, ID адресата | N:1 `Role`, 0..1 `Recipient` |
| `Role`, `RolePermission` | код, название, признак системной; набор прав | 1:N |
| `Recipient` | идентификатор, ФИО, дата рождения, e-mail, телефон, подразделение | 1:1 `Address`, 0..1 `RecipientArchive` |
| `Office` | название | 1:N `Notice`, `Recipient`, `Broadcast` |
| `Notice` | номер, даты, причина, комментарий, статус, автор, рассылка | N:1 `Recipient`, `Office`, `Broadcast` |
| `NoticeStatusHistory`, `AuditEvent` | статус/действие, пользователь, время | N:1 `Notice` |
| `Notification`, `DeliveryAttempt` | канал, адрес, состояние, ошибка; попытки | N:1 `Notice`; 1:N |
| `Appeal`, `Document` | обращения и метаданные документов | N:1 `Notice` |
| `Broadcast` | код, заголовок, текст, важность, каналы, аудитория, статус, счётчики | 1:N `Notice` |

Ограничения целостности: уникальны идентификатор адресата, название подразделения, номер оповещения, логин, код роли,
код рассылки; `ProcessingDeadline ≥ CreatedAt`; непустая причина; допустимые значения статусов, каналов, прав,
важности — CHECK-ограничения; параллельное изменение оповещения отслеживается по системному столбцу `xmin`.

## 7. Коды ответов

| Код | Когда |
|---|---|
| 200 | Успешное чтение или изменение |
| 201 | Ресурс создан (заголовок `Location`) |
| 202 | Массовое оповещение принято в обработку |
| 204 | Роль удалена |
| 400 | Некорректные данные |
| 401 | Нет или истёк JWT; неверный логин/пароль |
| 403 | Нет права; роль «только свои» без привязки |
| 404 | Не найдено или не видно пользователю |
| 409 | Конфликт бизнес-правил или параллельное изменение |
| 429 | Превышен лимит попыток входа |
| 501 | Доставка не настроена (`DEMO_ENABLED=false`) |
| 503 | `/api/ready`: БД недоступна |

Тело ошибки — `{ "error": "<текст на русском>" }` для всех маршрутов. [РЕШЕНИЕ: вместо `application/problem+json`]
