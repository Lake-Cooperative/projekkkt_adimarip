**Реестр оповещений «АДИМАРИП»**

Use Cases, функции системы и их описание — редакция 2.0 от 20.11.2026 (выпуск №70).
Полный контракт маршрутов — [`API.md`](API.md).

# 1. Общие сведения

Система представляет собой клиент-серверное веб-приложение для учета электронных оповещений, их статусов, истории
изменений, обращений, сопроводительных документов и массового оповещения работников.

Проект является учебным и демонстрационным и работает с вымышленными данными; доставка SMS и e-mail имитируется.

Технологический стек: React 18 + TypeScript + Vite (frontend); ASP.NET Core 8 Web API (backend); Entity Framework Core 8;
PostgreSQL 16; JWT-аутентификация; Swagger/OpenAPI; Docker Compose.

# 2. Должности, роли и права

Доступ определяется **правами**; роль — набор прав. Четыре роли ниже — системные (неизменяемые); инженер может
создавать кастомные роли с любым набором прав (UC-15).

| **Должность** | **Роль в системе** | **Права** |
|---|---|---|
| Секретарь | Operator | Весь реестр; создание оповещений, смена статусов, уведомления, обращения, документы; списание адресатов; массовое оповещение; история статусов |
| Управитель | Manager | Всё, что у секретаря, и журнал аудита |
| Служащий | Observer | Только свои оповещения; подтверждение получения; добавление документов к своим оповещениям |
| DevOps / инженер автоматизации | AutomationEngineer | Учётные записи, роли, создание адресатов-работников; запуск и проверка работоспособности; без доступа к реестру |
| Дежурный по безопасности (пример кастомной роли в демо-данных) | DutyOfficer | Весь реестр, адресаты, история; запуск и отчёты массовых оповещений |

# 3. Варианты использования

## UC-00. Вход в систему

**Должность:** все пользователи системы.

**Предусловие:** пользователь ещё не прошёл аутентификацию.

**Основной поток:** пользователь вводит логин и пароль; система проверяет их, создаёт JWT и показывает разделы,
доступные по правам его роли.

**Альтернативы:** неверные данные — 401; более 10 попыток в минуту — 429.

**Результат:** пользователь вошёл в систему; JWT используется для последующих запросов.

**API:** POST /api/auth/login, GET /api/auth/me.

## UC-01. Создание адресата

**Должность:** инженер автоматизации (право `RecipientsCreate`).

**Предусловие:** адресат с таким идентификатором отсутствует.

**Основной поток:** вводятся ФИО, дата рождения, контакты, подразделение и адрес; система проверяет уникальность
идентификатора и сохраняет данные. Обычно адресат-работник создаётся вместе с учётной записью (UC-11).

**Результат:** созданы записи Recipient и Address.

**API:** POST /api/recipients.

## UC-02. Создание оповещения

**Должность:** секретарь, управитель (право `NoticesCreate`).

**Предусловие:** существуют действующий адресат и подразделение.

**Основной поток:** пользователь задаёт номер, даты, причину и комментарий; система валидирует данные, сохраняет
оповещение со статусом `Created`, создаёт начальную запись истории и событие аудита — одной транзакцией.

**Альтернативы:** дата создания раньше трёх дней назад или срок раньше даты — 400; номер занят или адресат списан — 409.

**API:** POST /api/notices.

## UC-03. Просмотр реестра

**Должность:** секретарь, управитель — весь реестр; служащий — только свои оповещения.

**Результат:** таблица оповещений с фильтрацией по статусу, подразделению и строке поиска, с серверной пагинацией.
Оповещения массовых рассылок отмечены важностью.

**API:** GET /api/notices.

## UC-04. Просмотр карточки оповещения

**Результат:** отображаются адресат, подразделение, даты, текущий статус и разрешённые переходы, уведомления с
попытками доставки, обращения и документы; история статусов — при праве `HistoryView`, аудит — при `AuditView`.
Чужое оповещение служащему не показывается (404).

**API:** GET /api/notices/{id}.

## UC-05. Изменение статуса

**Должность:** секретарь, управитель (право `NoticesChangeStatus`).

**Правило:** допустимы только переходы конечного автомата (см. [`API.md`](API.md#оповещения)); каждый переход
фиксируется в NoticeStatusHistory и AuditEvent. Параллельное изменение той же записи — 409.

**API:** PATCH /api/notices/{id}/status.

## UC-06. Отправка уведомления (имитация)

**Должность:** секретарь, управитель (право `NotificationsSend`).

**Основной поток:** пользователь выбирает канал и адрес; система имитирует доставку, записывает попытки и итог
(`Delivered` или `Failed` с причиной). Пакетный вариант — до 50 выбранных записей на один тестовый адрес.
Реальная отправка SMS/e-mail не выполняется; вне демо-режима — 501.

**API:** POST /api/notices/{id}/notifications, POST /api/notices/notifications/bulk.

## UC-07. Регистрация обращения

**Должность:** секретарь, управитель (право `AppealsCreate`).

**Основной поток:** фиксируются тип обращения и текст; обращение привязывается к оповещению и получает статус `Submitted`.

**API:** POST /api/notices/{id}/appeals.

## UC-08. Добавление документа

**Должность:** секретарь, управитель; служащий — к своим оповещениям (право `DocumentsAttach`).

**Основной поток:** сохраняются метаданные документа: имя, MIME type и HTTPS-ссылка. Бинарный файл не принимается.

**API:** POST /api/notices/{id}/documents.

## UC-09. Просмотр истории

**Должность:** секретарь (история статусов), управитель (история и аудит).

**Результат:** последовательность изменений статусов и аудит действий в карточке оповещения.

**API:** данные приходят в составе GET /api/notices/{id}.

## UC-10. Проверка работоспособности

**Должность:** DevOps / инженер автоматизации.

**Основной поток:** выполняется `docker compose -f docker_compose.yml up --build`; открываются UI (порт 8080),
API (порт 8081) и Swagger (/swagger); `/api/ready` подтверждает соединение с БД.

**API:** GET /api/health, GET /api/ready.

## UC-11. Создание учётной записи

**Должность:** инженер автоматизации (право `UsersManage`).

**Предусловие:** логин ещё не занят.

**Основной поток:** инженер задаёт логин, имя, роль (системную или кастомную) и пароль. Если роль видит только свои
данные, дополнительно вводятся дата рождения, контакты и подразделение — система создаёт адресата и учётную запись
одной транзакцией и сообщает ID работника.

**Результат:** создана учётная запись (и при необходимости адресат).

**API:** POST /api/admin/users, GET /api/admin/users.

## UC-12. Массовое оповещение работников

**Должность:** секретарь, управитель, дежурный (право `BroadcastsSend`).

**Предусловие:** включён демо-режим доставки.

**Основной поток:**
1. Пользователь вводит заголовок и текст, выбирает важность, каналы и подразделение-отправитель.
2. Выбирает аудиторию: все работники, работники подразделений или выбранные люди; система показывает число получателей.
3. Запускает рассылку; система создаёт оповещение реестра каждому работнику, ставит рассылку в очередь и сразу отвечает.
4. Фоновый обработчик доставляет сообщения параллельно, повторяя временные сбои; оповещения переходят в `Delivered` или `Failed`.

**Альтернативы:** нет каналов, пустая аудитория, более 2000 человек — 400; вне демо-режима — 501.
Срочная рассылка обрабатывается вне очереди и по всем каналам с известными контактами.

**API:** POST /api/broadcasts/preview, POST /api/broadcasts.

## UC-13. Отчёт о рассылке

**Должность:** право `BroadcastsView`.

**Результат:** журнал рассылок; по выбранной — ход доставки (обновляется автоматически), итоги по каналам, список
недоставленных уведомлений с причинами и число подтвердивших получение.

**API:** GET /api/broadcasts, GET /api/broadcasts/{id}.

## UC-14. Подтверждение получения

**Должность:** служащий (право `NoticesAcknowledgeOwn`).

**Основной поток:** работник видит баннер срочного оповещения (или кнопку в карточке) и нажимает «Ознакомлен(а)»;
оповещение получает статус `Read`, событие попадает в аудит и в отчёт рассылки.

**Альтернативы:** повторное подтверждение — 409; чужое оповещение — 404.

**API:** POST /api/notices/{id}/acknowledge.

## UC-15. Управление ролями

**Должность:** инженер автоматизации (право `RolesManage`).

**Основной поток:** инженер создаёт роль (код, название, права) или копирует системную; изменяет или удаляет кастомную роль.

**Альтернативы:** изменение системной роли, удаление роли с пользователями, снятие `RolesManage` с собственной роли — 409.

**API:** GET /api/permissions, GET/POST /api/roles, PUT/DELETE /api/roles/{name}.

## UC-16. Смена роли пользователя

**Должность:** инженер автоматизации (право `UsersManage`).

**Основной поток:** инженер выбирает пользователю другую роль; права меняются со следующего запроса пользователя.

**Альтернативы:** снять с себя `UsersManage` или назначить роль «только свои» учётной записи без адресата — 409.

**API:** PUT /api/admin/users/{username}/role.

Коды ошибок API (тело `{ "error": "..." }`):

- 400 Bad Request — некорректные данные: формат, длина, даты, неизвестный статус, канал или право, пустая аудитория;
- 401 Unauthorized — нет или истёк JWT, неверный логин или пароль;
- 403 Forbidden — у роли нет нужного права;
- 404 Not Found — запись не найдена или не видна пользователю;
- 409 Conflict — дубликат, запрещённый переход статуса, параллельное изменение, ограничения ролей;
- 429 Too Many Requests — превышен лимит попыток входа;
- 501 Not Implemented — доставка не настроена (вне демо-режима).
