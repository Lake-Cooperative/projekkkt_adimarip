# Миграции PostgreSQL и контроль целостности

## Текущее состояние

- Базовые таблицы предметной модели: `202610100001_InitialDomainSchema`.
- Индексы и ограничения: `202610160002_QueryIndexes`, `202610160003_DomainChecks`.
- Архив адресатов: `202610160004_RecipientArchives`.
- Учётные записи: `202610190005_AppUsers` (включает миграцию ранее вручную созданной таблицы).

На стартовом этапе приложение применяет новые миграции через `Database.MigrateAsync()`.
Это упрощает учебное развёртывание. Для промышленного обновления необходимо
предварительно сохранить резервную копию БД, подготовить SQL скрипт миграций,
отдельно выполнить его в окне обслуживания и запускать приложение только после
успешного обновления базы.

## Критичное техническое ограничение

`AdimaripDbContextModelSnapshot.cs` в исходном репозитории является неполной заглушкой.
**Не генерируйте очередную миграцию поверх неё без восстановления snapshot.**
Пока не выполнена регенерация через полноценный .NET SDK / EF CLI, автоматическое
сравнение EF-моделей не является достоверным. Ручные миграции исходной серии
поддерживают существующие данные, но это не замена канонического snapshot.

После установки .NET SDK 8 и `dotnet-ef` версии 8 проверьте модель и получите
канонический snapshot в отдельной ревью-ветке. Не применяйте автоматически
сгенерированный повторный `CREATE TABLE` к базе с данными.

## Контрольные команды

```bash
docker compose -f docker_compose.yml ps
docker compose -f docker_compose.yml exec -T db sh -c   'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'   < tests/sql/schema-verification.sql
```

**Перед любыми миграциями** проверить бэкап на восстановление в отдельной БД.
