## 2. Назначение и цели создания системы

### 2.1. Назначение системы

АС «АДИМАРИП» предназначена для автоматизации учёта электронных оповещений, их статусов, истории изменений, уведомлений, обращений и метаданных сопроводительных документов. Система является **учебной и демонстрационной**, работает с вымышленными тестовыми данными и не предназначена для промышленной эксплуатации.

**Объект автоматизации:** деятельность ведомственной по ведению реестра оповещений.

### 2.2. Цели создания системы

1. Обеспечить единый реестр оповещений с возможностью поиска, фильтрации и постраничного просмотра.
    
2. Автоматизировать учёт адресатов и их контактных данных.
    
3. Обеспечить фиксацию истории статусов и аудита действий пользователей.
    
4. Разграничить доступ пользователей в соответствии с ролями: Operator, Manager, Observer, Automation Engineer.
    
5. Предоставить демонстрационную отправку уведомлений и регистрацию обращений.
    
6. Обеспечить запуск системы одной командой `docker compose up --build`.
    

**Критерии достижения целей:** успешное прохождение сценариев UC-00…UC-11; соответствие бизнес-правилам БП-1…БП-14.

## 3. Характеристика объекта автоматизации

Объект автоматизации — процесс ведения реестра оповещений в учебной демонстрационной среде. Условия эксплуатации: локальная или виртуальная машина с Docker Engine и Compose plugin. Персонал — пользователи четырёх ролей, прошедшие обучение работе с системой. Окружающая среда — стандартная офисная/учебная инфраструктура, без экстремальных воздействий.

## 4. Требования к системе

### 4.1. Требования к системе в целом

#### 4.1.1. Структура и функционирование

Система состоит из трёх компонентов:

- **UI** — React 18 + TypeScript + Vite, доступен на порту **8080**;
    
- **API** — ASP.NET Core 8 Web API, доступен на порту **8081**;
    
- **БД** — PostgreSQL 16, внутренняя сеть Docker.
    

Взаимодействие UI с API — только по HTTP/JSON. Защищённые запросы передают заголовок `Authorization: Bearer <JWT>`. Swagger UI доступен по пути `/swagger` на API. Режимы функционирования: Development (Swagger включён) и Production (Swagger отключён).

#### 4.1.2. Численность и квалификация персонала

- **Operator (Секретарь)** — чтение и изменение данных.
    
- **Manager (Управитель)** — чтение и изменение данных, просмотр истории и аудита.
    
- **Observer (Служащий)** — чтение, подача документов.
    
- **Automation Engineer** — создание учётных записей, запуск и проверка работоспособности.
    

Квалификация: базовые навыки работы с веб-интерфейсом; для Automation Engineer — навыки работы с Docker и командной строкой.

#### 4.1.3. Показатели назначения

- Реестр загружается постранично, `pageSize` от 1 до 100.
    
- Отклик списка на тестовом наборе до 10 000 оповещений — не более 1 с (ориентировочно, уточняется).
    
- Время отклика `GET /api/health` — не более 1 с.
    

#### 4.1.4. Требования к надёжности

- Операции с несколькими записями (создание оповещения, смена статуса, создание адресата) выполняются в одной транзакции.
    
- Сохранность данных обеспечивается PostgreSQL 16 и volume `pgdata`.
    
- При аварийном завершении API незавершённые транзакции откатываются.
    

#### 4.1.5. Требования безопасности

- Пароли хранятся только в виде хеша (PBKDF2 или bcrypt), в открытом виде не хранятся и не логируются.
    
- Секрет подписи JWT и строка подключения к БД задаются переменными окружения, не хранятся в репозитории.
    
- Все защищённые endpoint проверяют JWT и роль на стороне сервера; скрытие кнопок в UI не заменяет серверную проверку.
    
- Входные данные валидируются на сервере; запросы к БД параметризованы (EF Core).
    

#### 4.1.6. Требования к эргономике

Интерфейс на русском языке; даты отображаются в формате ДД.ММ.ГГГГ. UI работает в актуальных версиях Chrome, Firefox, Edge.

#### 4.1.7. Требования к защите информации от НСД

Доступ к бизнес-данным реестра предоставляется только ролям Operator, Manager, Observer. Automation Engineer не имеет доступа к бизнес-данным. При нехватке прав возвращается **403**; без токена или с истёкшим токеном — **401**. Система должна полностью соответствовать **Федеральному закону от 27.07.2006 N 152-ФЗ «О персональных данных»** в последней редакции.

#### 4.1.8. Требования по стандартизации и унификации

Используются: OpenAPI для описания API; `application/problem+json` для ошибок; единый формат ответов списка (`items`, `page`, `pageSize`, `total`, `totalPages`). Документация ведётся в формате Markdown.

### 4.2. Требования к функциям (задачам)

|№|Функция|Endpoint|Роли|Источник|
|---|---|---|---|---|
|1|Вход в систему|`POST /api/auth/login`|Все|UC-00|
|2|Создание учётной записи|`POST /api/users`|Automation Engineer|UC-11|
|3|Поиск адресатов|`GET /api/recipients?search=`|Operator, Manager, Observer|UC-01|
|4|Создание адресата|`POST /api/recipients`|Operator, Manager|UC-01|
|5|Список подразделений|`GET /api/offices`|Operator, Manager, Observer|UC-02, UC-03|
|6|Реестр оповещений|`GET /api/notices`|Operator, Manager, Observer|UC-03|
|7|Карточка оповещения|`GET /api/notices/{id}`|Operator, Manager, Observer|UC-04|
|8|Создание оповещения|`POST /api/notices`|Operator, Manager|UC-02|
|9|Смена статуса|`PATCH /api/notices/{id}/status`|Operator, Manager|UC-05|
|10|Отправка уведомления|`POST /api/notices/{id}/notifications`|Operator, Manager|UC-06|
|11|Регистрация обращения|`POST /api/notices/{id}/appeals`|Operator, Manager|UC-07|
|12|Добавление документа|`POST /api/notices/{id}/documents`|Operator, Manager, Observer|UC-08|
|13|Просмотр истории и аудита|в составе `GET /api/notices/{id}`|Manager|UC-09|
|14|Проверка работоспособности|`GET /api/health`|без авторизации|UC-10|

**Временные решения по открытым вопросам:** endpoint входа — `POST /api/auth/login`; создание учётных записей — `POST /api/users`; начальный статус оповещения — `Created`; переходы статусов — любой, кроме повтора текущего; история и аудит — только Manager; документы — `POST /api/notices/{id}/documents`; каналы уведомлений — минимум `Email`; типы обращений — свободная строка, пример `Clarification`; автор оповещения — из JWT; дубликат адресата — 409; формат ошибок — `application/problem+json`.

### 4.3. Требования к видам обеспечения

#### 4.3.1. Математическое обеспечение

Специальных математических методов не требуется. Используются стандартные алгоритмы пагинации, фильтрации и поиска.

#### 4.3.2. Информационное обеспечение

**Сущности БД:** `Recipient`, `Address`, `Office`, `Notice`, `NoticeStatusHistory`, `AuditEvent`, `Notification`, `DeliveryAttempt`, `Appeal`, `Document`. Будущая сущность `User`/`Account` — на этапе M2.

**Ограничения целостности:** уникальность `Recipient.ExternalIdentifier`, `Office.Name`, `Notice.Number`, `Address.RecipientId`; `Notice.ProcessingDeadline >= Notice.CreatedAt`; непустая `Notice.Reason`.

**Формат данных:** даты — `DateOnly`, время событий — `DateTimeOffset`.

#### 4.3.3. Лингвистическое обеспечение

Язык программирования: C# (backend), TypeScript (frontend). Язык взаимодействия с пользователем: русский. Кодировка: UTF-8.

#### 4.3.4. Программное обеспечение

| Слой             | Технология                 |
| ---------------- | -------------------------- |
| Frontend         | React 18, TypeScript, Vite |
| Backend          | ASP.NET Core 8 Web API     |
| ORM              | Entity Framework Core 8    |
| СУБД             | PostgreSQL 16              |
| Аутентификация   | JWT (Bearer)               |
| Документация API | Swagger / OpenAPI          |
| Развёртывание    | Docker Compose             |

**Покупные программные средства:** `Microsoft.EntityFrameworkCore` 8.0.11, `Npgsql.EntityFrameworkCore.PostgreSQL` 8.0.10 (выровнять версии до 8.0.11 перед M2).

#### 4.3.5. Техническое обеспечение

Требуется машина с Docker Engine + Compose plugin, доступ к Docker Hub, NuGet, npm. Минимальные характеристики: 2 ядра CPU, 4 ГБ ОЗУ, 20 ГБ свободного дискового пространства.

#### 4.3.6. Организационное обеспечение

**Роли и доступ:** Operator, Manager, Observer, Automation Engineer. **Режим работы:** учебный, по расписанию семинаров. **Взаимодействие персонала:** через веб-интерфейс UI и Swagger для API.

## 6. Порядок контроля и приёмки системы

### 6.1. Виды испытаний

В соответствии с ГОСТ 34.603-92:

- **Автономные испытания** — проверка отдельных компонентов (API, UI, БД).
    
- **Комплексные испытания** — проверка взаимосвязанных частей системы.
    
- **Предварительные испытания** — определение работоспособности и возможности приёмки в опытную эксплуатацию.
    
- **Опытная эксплуатация** — проверка фактических характеристик.
    
- **Приёмочные испытания** — проверка соответствия требованиям ТЗ.
    

### 6.2. Критерии приёмки семинара 2

1. `docker compose -f docker_compose.yml up --build` собирает три сервиса.
    
2. `curl http://localhost:8081/api/health` возвращает JSON с `status: ok`.
    
3. `http://localhost:8080` отображает брендированную главную страницу и статус API.
    
4. `http://localhost:8081/swagger` открывается при `ASPNETCORE_ENVIRONMENT=Development`.
    

**Фактическая проверка в Docker не подтверждена** — требуется прогон на машине с Docker.

### 6.3. Статус приёмочной комиссии

Ведомственная (учебная). Состав: представители заказчика и разработчика.

## 7. Требования к подготовке объекта автоматизации

1. **Приведение информации к виду, пригодному для обработки:** тестовые данные готовятся вручную или скриптом начального заполнения.
    
2. **Изменения в объекте автоматизации:** не требуются (учебная демонстрационная система).
    
3. **Создание условий функционирования:** машина с Docker, доступ к реестрам пакетов и образов.
    
4. **Создание подразделений и служб:** не требуется.
    
5. **Комплектование штатов и обучение персонала:** пользователи проходят инструктаж по работе с UI и Swagger.
