# Решения по данным и статусам

Актуально на 20.11.2026 (выпуск №70). Схема — [`erd.md`](erd.md), маршруты — [`API.md`](API.md).

## Хранение

- Все таблицы, включая `AppUsers`, `Roles`, `RolePermissions`, `RecipientArchives` и `Broadcasts`, создаются
  версионными миграциями EF Core и отображены на доменные сущности; ручного SQL в коде приложения нет.
- Пароли — только PBKDF2-хеши (ASP.NET Core Identity `PasswordHasher`); формат совместим с прежними выпусками.
- Перечисления (статусы, каналы, права, важность) хранятся строками; допустимые значения закреплены CHECK-ограничениями.
- Параллельные изменения оповещения обнаруживаются по системному столбцу `xmin` (оптимистическая блокировка).

## Роли и доступ

- Доступ определяется правами; роль — набор прав (`Roles` + `RolePermissions`). Четыре исходные роли — системные.
- Роль «только свои данные» (`NoticesReadOwn` без `NoticesReadAll`) требует привязки учётной записи к адресату
  (`AppUsers.RecipientId`). Для `Observer` это закреплено и CHECK-ограничением.
- Права и привязка читаются из БД на каждый запрос; токен содержит только логин (остальные поля — для удобства UI).

## Оповещения и статусы

- Начальный статус — `Created`. Допустимые переходы задаёт сервер (`NoticeLifecycle`), интерфейс получает их в карточке.
- При создании записи сразу фиксируются начальная история и аудит; статус, история и аудит сохраняются одной транзакцией.
- Подтверждение получения доводит статус до `Read` через разрешённые переходы и пишет событие `Acknowledged`.

## Уведомления

- Доставка **имитируется**. `Notification.Status`: `Pending` (в очереди), `Delivered`, `Failed` (+ `LastError`).
  Каждая попытка — строка `DeliveryAttempts` (`Delivered`/`Failed`). `Delivered` — результат имитации, не подтверждение
  стороннего провайдера.
- Уведомления, записанные до миграции `202611190006`, получили статус `Delivered` (так они и отображались).
- Вне демо-режима отправка отвечает 501.

## Массовое оповещение

- `Broadcasts` — сводка рассылки; каждому работнику создаётся обычное оповещение реестра с `BroadcastId`.
- Очередь рассылок живёт в памяти процесса, источник истины — БД: незавершённые рассылки (`Queued`, `Dispatching`)
  восстанавливаются при старте. Обработка идемпотентна: уведомления не в статусе `Pending` повторно не отправляются.

## Документы и списание

- Документы — только метаданные и HTTPS-ссылка, без бинарного содержимого.
- `RecipientArchives` — одна запись на адресата: причина, дата, логин инициатора. Списание не стирает оповещения
  и журналы; списанный адресат скрыт из справочника и рассылок, его исторические карточки доступны.

## Совместимость

Изменения рассчитаны на БД, управляемую миграциями. Перед обновлением важного тома сделайте резервную копию
(`scripts/backup-db.sh`). Если таблицы создавались вручную или через `EnsureCreated`, используйте чистую демонстрационную БД.
